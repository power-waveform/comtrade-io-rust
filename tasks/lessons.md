# Lessons

本文件记录用户纠正与自查发现的错误模式，以及防止复发的规则。每次会话开始前先复习。

---

## L1：重命名必须"定义 + 全部调用点"原子完成

**发生了什么**（2026-08-14，命名审查）
我在 `src/cfg/mod.rs` 与 `src/dat/mod.rs` 改了方法**定义**名，还没改调用点就被中断。
恢复后跑基线 `cargo test`，5 个 E0599 —— 我把仓库留在了编译不过的状态，而且一开始
误以为那是既有问题。

**规则**
- 重命名要么一次改完定义与所有调用点，要么不动。不做"先改定义，回头再扫调用点"。
- 改名前先 grep 出全部调用点，把它们列进本次编辑范围。
- **任何中断（用户打断、上下文切换）恢复后，第一件事是 `cargo build`**，确认自己没留下
  半成品状态，再谈下一步。不要把自己造成的破坏读成"原有缺陷"。

## L2：变异测试要先确认变异真的生效了

**发生了什么**（2026-08-14，`nominal_freq` 修复）
为验证新写的 6 个测试真能抓到 bug，我用 `python3` 精确字符串替换把代码回退成有 bug 的样子。
替换**静默匹配零处**（因为 `cargo fmt` 已经把那段代码重排过），于是测试实际跑在**已修好**的
代码上，6 个全过。我差点把这个毫无意义的结果当成"测试有效"的证据。

grep `with_cycle_point_num` 才发现回退没生效；改用 Edit 工具重做，确认 **6 项中 4 项 FAILED**，
才真正证明测试有鉴别力。

**规则**
- 精确字符串替换**必须**校验命中数。`sed`/`python3 .replace()` 匹配失败是静默的。
  能用 Edit 工具就用 Edit（不匹配会报错）。
- 变异测试的正确判据是"**测试失败了**"。如果变异后测试仍全过，第一假设是
  **变异没打上**，而不是"测试不敏感"。
- 格式化工具跑过之后，所有基于旧文本的精确匹配脚本都可能失效。

## L3：用户的措辞可能与规范冲突——先澄清，别照字面实现

**发生了什么**（2026-08-14，`nominal_freq`）
用户说"按额定频率**校准**修一下"。但查 Python 基线后确认：`nominal_freq` **从不校准
`samp_rate`**（采样率完全由时间戳差值决定），它只用来派生每周波采样点数
`cycle_point_num = samp_rate / freq`。照字面实现"校准采样率"会引入一个基线里不存在的行为。

我把这个矛盾摆出来问了用户，用户选择对齐 Python 语义。

**规则**
- 用户描述与权威规范（Python 基线 / `docs/` 设计报告 / IEEE C37.111）冲突时，
  **摆出矛盾并询问**，不要静默选一边——尤其不要选"字面正确但语义错误"的那边。
- 提问时同时给出两个选项的具体后果，而不是只说"我不确定"。

## L4：死参数/死代码往往是模型缺字段的症状，不是病本身

**发生了什么**（2026-08-14）
`recalculate_segments` 的 `nominal_freq` 参数从未被读取。表面看是"忘了用"，改法似乎是
"用上它或删掉它"。实际根因是 **Rust 的 `Segment` 结构体比 Python 基线窄** —— 基线有
`start_point` / `count` / `cycle_point_num` 三个字段，Rust 一个都没有，派生值无处安放，
参数只能烂在签名里。

**规则**
- 遇到死参数/死变量，先问"**它本该写到哪里去？**"。如果答案是"没有那个字段/那个结构",
  真正的修复是补模型，不是删参数。
- 有 Python 基线可比对时，**逐字段对比数据结构**，别只对比函数行为。

## L5：配置文件必须与实际生效行为一致，不生效的项要么删要么标注

**发生了什么**（2026-08-14，rustfmt.toml）
用户给的 22 项配置里，**11 项是 nightly-only**，在 stable 上被**静默忽略**；还有 1 项
（`impl_empty_lines`）rustfmt 根本没有这个选项。原样留着，配置文件就在谎报格式化行为。

**规则**
- 写完配置**必须实际跑一次**并读完警告输出，确认每项都生效。
- 不生效的项：注释掉 + 标注生效条件（如 `[nightly]`），别留在活动配置里。
- 副作用要写进 CLAUDE.md：本项目 `imports_granularity` / `group_imports` / `wrap_comments`
  未生效，导入不合并、注释不重排——后人否则会误以为这些规则在跑。

## L6：不要用没验证过的 shell 一行流报告数字

**发生了什么**（2026-08-14）
我用一条 `awk -F'[;:] ' '{s+=$2}'` 管道统计测试数，输出 "total passed: 0" —— 明显错误
（实际 70 项通过）。差点把这个数字报给用户。

**规则**
- 报告给用户的数字，要么来自**工具原始输出**，要么来自**验证过的**统计命令。
- 一行流出来的数字如果与直觉不符（比如 0），先怀疑一行流，别怀疑代码。

## L7：只断言"不 panic"的测试等于没有测试

**发生了什么**（设备模型那轮，记录于 `todo.md`）
`test_to_equipment_group` 只写 `let _ = eg.buses.len();`。于是"7 个母线名字全为空、
绕组数为 0"这种整段解析失效长期没被发现。

同样，`recalculate_segments` 此前**零测试**，`nominal_freq` 死参数才能一直活着。

**规则**
- 测试必须断言**具体字段值**，不能只断言"没崩"。
- 新增/修改函数时，先看它现有测试覆盖如何；**零覆盖的函数是缺陷高发区**，
  这类地方要连不变式一起测（如"相邻段首尾相接、无空隙无重叠"）。
